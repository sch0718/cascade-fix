## 측정 중 생긴 일

1. **표본 문서가 git 밖에 있었다.** sample-infra는 `docs/superpowers/`를 `.gitignore`와 `.git/info/exclude`로 빼 두어 문서가 어느 커밋에도 없었다. 그래서 replay가 커밋 워크트리에서 문서를 찾지 못한다. 원래 저장소는 건드리지 않았다. 대신 `git clone --shared`로 사본을 만들고, 문서 머리에 적힌 기준 커밋 `3496948a`(feature/replay-validation) 위에 설계 문서와 관련 메모를 `add -f`로 커밋해 표본 저장소로 썼다.
2. **「참조 실존」 검사가 판가름 채택을 막았다.** 문서 모드는 판가름 패치에도 문서 검사(`cascade/cli.py:662`의 `_adjudicate_verify` → `doc_checks`)를 돌린다. 이 검사가 3건에서 실패했다. 실패한 참조는 Claude 02의 `replay.example.com/description`·`replay.example.com/display-name`, 외부 01의 `values-local.yaml`, 외부 04의 `execute-left/right`·`finalize-left/right`다.
   - 원인: 검사가 문서가 새로 정하는 이름(DAG 노드), 라벨·어노테이션 키, 경로를 줄여 쓴 파일 이름(실제 파일은 `20. Helm/replay-runner/values-local.yaml`)을 모두 저장소에 없는 참조로 본다.
   - 결과: Opus가 「사실·작성자 패치 채택」이라 하고 검토자 의견도 「채택 가능」이라 했는데 판단불가로 끝났다.
   - 작업자 종류와 무관한 문서 모드의 구조 문제다. 다만 외부 작업자 쪽에서 판가름이 더 자주 열려 더 많이 걸렸다(외부 2건, Claude 1건).
3. **재검토 단계는 돌리지 않았다.** apply가 재검토 프롬프트를 만들었다(Claude 작업자 4건, 외부 작업자 2건). 비교 대상은 1회차 작업자이고 `replay.py` 채점도 1회차 판정만 보므로 두 구성 모두 건너뛰었다. 재검토가 새 지적을 내는 비율은 이번에 재지 않았다.
4. **Claude 작업을 단계별로 묶어 돌렸다.** 항목마다 Workflow를 띄우지 않았다. 작업 id 앞에 항목 이름을 붙여 단계마다 Workflow 하나로 묶고(stage1 21개, 점검자 5개, 판가름 2·3개, 의견 1·2개), 결과를 항목별 `stage1.json` 등으로 다시 나눴다. 모델·프롬프트·스키마는 스킬의 `scripts/run-jobs.js` 그대로다.
5. **검토자를 Claude로 고정했다.** 두 구성 모두 `CASCADE_REVIEWER=claude`로 돌렸다. 바뀌는 것은 작업자 자리뿐이다.
6. **측정 전 커밋.** 이 브랜치에 PR의 10-19 수정 커밋 4개(`7ba9761 c6aa721 d6727c6 f54c9fb`)를 cherry-pick했다. 전체 테스트 573개가 통과했다.

## 다음

- 기본값은 바꾸지 않는다. 문서 모드의 `--workers external`은 옵션으로 남긴다.
- 이번 표본(지적 7건, 정답 4건)으로는 기본값을 판단할 근거가 부족하다. 다시 잰다면 문서 여러 개로 지적 30건 이상을 모으고, 「아님」이 섞이도록 초안 단계의 문서를 고른다. 이번 문서는 이미 「설계 합의 완료」 상태라 7건 모두 「사실」 쪽이었다.
