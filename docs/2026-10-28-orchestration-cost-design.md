# 진행 비용 줄이기 설계안 (2026-10-28, 초안)

`docs/2026-10-26-cost-effectiveness.md`가 잰 「진행 비용」(메인 세션이 단계를 이어 가는 몫, 지적당 약 $0.80)을 어떻게 줄일지 조사한 설계안이다. 목표는 지적당 약 $0.34 아래다(그래야 `local`이 단일 Claude와 같아진다). 이 문서는 기존 기록(진행 비용 7회의 세션 JSONL)만 읽어 추정했고 유료 모델은 돌리지 않았다. 초안을 쓸 때는 코드를 바꾸지 않았다. 이후 (a-lite)는 구현해 main에 병합했다(3절, PR #31). (a-full)·(d) 등 나머지는 설계 단계다.

## 요약

- **진행 비용은 `요청 수 × 메인 세션 맥락 길이`로 거의 정해진다.** 7회에서 두 값의 곱과 비용의 상관이 0.98이다(요청 수만으로는 0.54). 비용의 76%가 캐시 읽기(요청마다 쌓인 대화를 다시 읽음), 출력 10%, 캐시 쓰기 9%다.
- 7회의 메인 세션은 이미 길었다(실행 첫 요청 때 맥락 145k~671k 토큰, 가중 평균 약 345k). 단계 출력은 한 번에 수백~수천 자로 작다(`report`만 2.4k~10k자). **그래서 결과 출력을 줄이는 (c)는 효과가 3% 안팎이다.**
- 기존 문서의 「고정 $1.04 + 지적당 $0.50」은 지적 수와 맥락 길이가 함께 큰 표본(상관 0.78)이 만든 모양이다. 지적이 많은 실행이 더 긴 세션에서 돌았다. 지적당 $0.50은 지적 하나가 드는 비용이라기보다 긴 세션에서 도는 비용으로 읽어야 한다.
- 효과가 큰 것은 요청 수를 줄이는 것(a)과 맥락을 작게 하는 것(새 맥락에서 돌리기, 이 문서의 (d))이다. 모델을 가볍게 하는 (b)는 단가표에서 Opus와 Sonnet의 캐시 읽기 단가가 같아(0.20) Haiku만 의미가 있다.
- **추천: (a-lite, 구현·병합됨) → 실사용 재측정 → (a-full, 설계 단계). (d)는 서브에이전트에 Workflow가 없음을 확인해 하지 않기로 했다.** (a-lite)만으로 지적당 약 $0.30, (a-full)까지 하면 약 $0.13으로 추정한다(둘 다 미측정). $0.13은 검토 칸이 Codex·Cursor인 프로필(`local` 계열)에서 작업 역할만 옮겨도 성립하는 값이고, 검토 칸이 Claude인 프로필은 검토 역할까지 옮겨야 한다(`docs/2026-10-28-claude-runner-design.md` 3.2). 판정 품질은 어느 것도 건드리지 않는다(판정은 이미 스크립트·작업자·판가름이 한다).

## 1. 현재 흐름과 메인 세션 요청

절차(SKILL.md 「절차」): init → jobs → Workflow(1단계) → CF usage → judge → Workflow(판가름) → CF usage → adjudicate → (의견) → apply → (재검토) → report → cleanup. 메인 세션이 하는 일은 명령 호출, Workflow 도구 호출, Workflow 결과를 파일로 옮기기, 알림 기다리기다. 판정·채택·테스트는 이미 `cascade/` 스크립트가 한다.

7회(214 요청, $19.32)의 요청을 종류별로 나눴다. 한 요청이 여러 도구를 부르면 첫 종류로 센다.

| 종류 | 요청 | 비용 | 하는 일 |
| --- | ---: | ---: | --- |
| CF 단계 명령(init·jobs·judge·adjudicate·apply·report·cleanup·usage 등) | 75 (35%) | $7.57 (39%) | 출력은 대부분 500~1,200자, `report`는 2.4k~10k자 |
| 기타 Bash | 77 (36%) | $6.05 (31%) | 백그라운드 출력 확인(`cat …/tasks/*.output`), Workflow 결과 JSON 저장(`python3 -c …`), 조사·뒷정리 |
| 텍스트만(알림 뒤 진행 한 줄 등) | 45 (21%) | $3.92 (20%) | 도구 호출 없는 응답 |
| Workflow 도구 | 17 (8%) | $1.78 (9%) | 스크립트·args 넘기기 |

- 한 요청의 비용은 거의 `맥락 × $0.20/MTok`이다(요청당 $0.05~$0.16, 맥락 170k→700k). 맥락이 짧은 세션(≈170k)에서 가장 깨끗한 1건 실행(4b33636c)도 25 요청, $1.24였다.
- 요청 수는 지적 수에 크게 기대지 않는다(1건 실행 25·25 요청, 7건 27 요청, 5건 39 요청). 늘어나는 것은 조사·보류 후보 선택·재검토 같은 곁가지다.
- **사실로 확인한 구조**: Workflow는 하네스 도구라 스크립트가 부를 수 없다. 그래서 지금은 Claude 작업(1단계 작업자 B가 Haiku·Sonnet일 때, 판가름, Claude 의견·재검토)이 있을 때마다 메인 세션이 Workflow를 띄우고 그 결과를 파일로 옮겨야 한다. `scripts/run-jobs.js` 하나가 모든 Claude 호출을 한다.
- `CF workers`는 이미 Codex·Cursor 작업을 한 명령으로 돌리고 결과를 파일에 쓴다. Claude를 `claude -p`로 돌리는 경로는 `cascade/`에 없다(`eval/solo.py`에만 있다).

## 3. 후보별 설계와 위험

### (a-lite) Workflow는 두고 명령을 합친다 — 구현됨

이 절은 설계 당시 이름(`start`·`after-stage1`·`finish`)이 아니라 구현된 모양을 적는다. 구현은 main에 병합됐다(PR #31, 병합 커밋 c918ff4, 이 브랜치의 구현 커밋 20688b9. 병합 사실은 세션 메시지 기준이다).

- 구현한 것: 새 명령 둘. `CF start <init 인자>`는 `init` 뒤 `jobs`까지 잇고(1단계 작업이 10개를 넘고 `--severity`가 없으면 `init`에서 멈춰 규모를 묻게 한다), `CF go --run-dir R [--workflow-output F --workflow W --allow-repro F]`는 Workflow 결과를 저장하고 `usage`를 한 뒤 `judge`·`adjudicate`·`opinion`·`apply`·`recheck`·`report`를 멈출 곳까지 잇는다. 두 명령은 기존 `cmd_*`를 `main()`으로 불러 판정 로직을 건드리지 않는다. 다음 단계 계산은 `next_steps`를 구조화한 `next_actions`로 한 벌만 유지한다. SKILL.md 「절차」에 「기본 경로: start와 go」를 더했고 단계 사이 진행 한 줄 알림 문장은 뺐다.
- 설계 때와 달라진 점: 명령이 셋(`start`·`after-stage1`·`finish`)이 아니라 둘이다. Workflow 알림의 output-file JSON에는 실행 id(`wf_…`)가 없어 `--workflow wf_…`는 메인 세션이 따로 넘긴다(샘플 1건 확인). `workers.lock`(실행 폴더당 `workers` 하나)과 모델 ID 경고 멈춤(출력 줄 검사), 끝나지 않은 단계에 새 Workflow 결과를 주면 바꾸는 규칙은 구현 뒤 Codex 교차 리뷰에서 나온 지적을 재현해 추가한 것이다. SKILL.md 줄이기(실측 기록·외부 작업자 칸 설명 옮기기)는 이번 범위가 아니라 하지 않았다.
- 사람 개입 지점: 그대로다. 종료 코드 4·5·6은 그 코드로 끝나고, 재현 명령 승인(`--allow-repro`)·모델 ID 경고·`workers`가 돌고 있을 때·`report` 뒤(`cleanup`은 하지 않는다)에서 `멈춤: 이유`와 `다음:`을 출력하고 멈춘다. 보류 후보 선택은 `cleanup` 전 사람 단계다.
- 아직 확인하지 못한 것: 실제 사용 세션에서 돌린 적이 없다. 요청 약 12건·지적당 약 $0.30은 이 흐름을 그려 센 추정이다. `go` 안에서 Codex·Cursor 스크립트를 돌리는 경로와 PR 재현 명령 승인 멈춤은 자동 테스트로 덮지 못했다. 긴 세션(맥락 500k↑)에서는 12 요청만으로도 $0.4 이상이라 목표를 못 맞춘다.
- 판정 품질 영향: 없음(같은 함수·같은 순서).

### (d) 새 맥락에서 돌리기(서브에이전트 또는 헤드리스 오케스트레이터)

- 아이디어: 사용자의 긴 메인 세션이 단계를 잇지 말고, 맥락이 작은 서브에이전트(Agent 도구, `model` 지정 가능)가 SKILL 절차를 돌리고 요약만 메인에 돌려준다. 맥락 40~60k 토큰(시스템·SKILL·도구 정의 가정, 미측정)이면 같은 요청 수로도 지적당 약 $0.28~0.34, Haiku면 약 $0.16이다.
- 시험 결과(2026-10-28, general-purpose 서브에이전트 Haiku 1건, 도구 호출 없이 자기 도구 목록만 보고하게 함): `Workflow`·`AskUserQuestion`은 없고 `Bash`·`Agent`는 있다. 자기 보고 1건이라 다른 서브에이전트 유형이나 설정에서는 다를 수 있다. 이 결과대로면 서브에이전트가 SKILL의 Workflow 단계를 직접 돌릴 수 없으므로 **(d)는 (a-full)(Claude 호출을 `claude -p`로 스크립트화)이 선행 조건**이다. 서브에이전트는 Bash로 `CF` 명령만 잇는다.
- 한계: ① 사람 확인(AskUserQuestion)은 서브에이전트가 못 하므로 멈추는 곳마다 메인에 돌려줘야 한다. ② 서브에이전트 비용은 이용 한도에 그대로 잡힌다. ③ 사람 개입(계획 확인·동의·보류 후보 선택)은 메인 세션에 남기고, 서브에이전트는 「init~report」만 맡는 식으로 나눠야 한다.
- 공정성: 기존 비교의 단일 Claude는 빈 맥락 헤드리스라 cascade-fix에 불리하게 기울어 있었다(`docs/2026-10-26-cost-effectiveness.md` 한계). (d)는 같은 조건으로 맞춘다.

### (a-full) Claude 호출까지 스크립트로 — 설계 단계(별도 문서)

구체 설계는 `docs/2026-10-28-claude-runner-design.md`에 있다. 새 `CF run`이 아니라 구현된 `go`를 확장하는 안으로 바뀌었다. 아래는 이 문서를 쓸 때의 위험 목록이고, 설계 문서가 코드 리뷰 뒤 보강한 위험(사용자 저장소를 읽는 역할에 `_run_isolated`를 쓰면 인덱스 훼손, 모델 ID 접두사 불일치, 판가름·Claude 대체 실행의 `workers` 계약 누락, 한도·로그인 뒤 재개 규칙, 사용량 누락 계산, 중단 경계)은 그 문서에 있다.

- 아이디어: `CF workers`가 이미 Codex·Cursor 작업을 돌리듯 Claude 작업(작업자 B, 판가름, Claude 의견·재검토)도 `claude -p`로 돌리게 한다(`eval/solo.py`가 같은 방식으로 `--json-schema`·`--effort`·`--setting-sources project --strict-mcp-config` 사용). 그러면 init → … → report를 `go`가 이어 가고 멈출 때만 사람에게 돌아온다. 메인 세션은 시작·결과 전달 약 5 요청이다.
- 위험(큼):
  1. 작업 격리: Workflow 서브에이전트가 받던 권한과 `claude -p --permission-mode acceptEdits --allowedTools Bash`는 다르다. 워크트리 밖 쓰기를 막는 장치(`judge`·`adjudicate`의 사용자 저장소 변경 검사, 종료 코드 6)가 이미 있어도, 작업 중 막는 것은 아니다. Codex·Cursor 경로가 가진 샌드박스·읽기 제한을 Claude 경로에 맞추는 설계가 필요하다.
  2. 사용량: `CF usage`는 Workflow 기록 폴더를 읽는다. `claude -p`는 `total_cost_usd`와 세션 기록을 따로 주므로 `claude-usage.json` 기록 방식을 새로 만들어야 한다(보고서 「역할별 사용량」).
  3. 사용자 설정 오염: 사용자 `CLAUDE.md`·훅·MCP가 작업자에 실리지 않게 해야 한다(solo.py는 `--setting-sources project`). 이 기기의 `~/.claude/CLAUDE.md`는 그 설정으로도 실렸다는 점을 지난 측정이 기록했다.
  4. Workflow 사용 동의(SKILL.md 59행: 계획 확인이 곧 Workflow 요청)의 의미가 바뀐다. `claude -p` 호출은 별도 동의 문구가 필요하다.
  5. 병렬성·시간 제한: Workflow가 하던 동시 실행·재시도를 `CF workers` 풀(CLI별 4개, 900초)로 옮겨야 한다.
  6. 측정 필요: 작업자 판정이 바뀌지 않는지(같은 프롬프트·모델·effort라면 같아야 하나 호출 방식이 달라 통계적으로 확인해야 한다). 이는 유료 측정이라 이 단계에서는 하지 않았다.

### (b) 가벼운 모델 · (c) 짧은 출력

- (b)는 위 표와 같다. Haiku로 본 세션을 돌리는 방법은 사용자의 세션 모델을 바꾸는 것이라 (d)의 서브에이전트 `model` 지정으로만 의미가 있다.
- (c): 단계 출력이 이미 짧아(CF 단계 명령 요청 75건의 결과가 대부분 500~1,200자) 효과가 3% 안팎이다. `report` 출력만 한 번 읽히는 4k~10k자이므로, 보고서는 파일로 두고 요약만 출력하는 정도는 (a-lite)에 곁들일 수 있다.

## 4. 추천 순서와 근거

1. **(a-lite) — 구현됨**: 위험이 낮고 되돌리기 쉽다. 기존 함수를 부르는 명령이라 판정 품질이 그대로이고, 사람 개입 지점(종료 코드, 승인, 보류 후보 선택)이 바뀌지 않는다. 지적당 약 $0.30으로 목표 경계다. 맥락이 긴 세션에서는 부족할 수 있다.
2. **(d) 가능성 확인(완료)**: 서브에이전트에는 Workflow·AskUserQuestion이 없었다. (d)는 (a-full) 없이는 안 된다.
3. **(a-full)**: 1번 조건(서브에이전트 40~60k)을 택했으나 (d)는 하지 않기로 했고, (a-full)은 (a-lite)의 `go`를 확장하는 별도 설계(`docs/2026-10-28-claude-runner-design.md`)로 이어진다. 가장 크고 위험도 가장 크다(작업 격리·사용량·모델 ID 검증·재개·측정). (a-lite) 실사용 측정 뒤 정하는 것이 안전하다.
4. **(b)·(c)** 단독으로는 하지 않는다. (b)는 (d)와 함께 서브에이전트 모델 선택으로 남기고, (c)는 `report` 요약 정도만 (a-lite)에 곁들인다.

## 5. 사람이 정할 결정

정한 것(2026-10-28):

1. 목표 조건: 처음에는 「새 맥락 서브에이전트(40~60k)에서 지적당 $0.34 아래」로 정했으나, (d)가 안 되는 것을 확인한 뒤 「(a-full) 뒤 현재 세션 맥락에서 $0.34 아래」로 바꿨다(`docs/2026-10-28-claude-runner-design.md`).

4. (d) 가능성 확인 시험은 승인했고 3절에 결과를 적었다(서브에이전트에 Workflow 없음). (d)는 하지 않는다.

6. 개선 뒤 진행 비용을 어떻게 다시 잴지: 지금 7회 측정 방식(`eval/orchestration_cost.py`)을 쓰고 실제 사용 5회 이상을 모은다. 단 `find_runs`가 `report` 없는 실행(중단·실패)을 버리므로 완료·중단·재시도를 함께 기록하고 성공당 비용과 전체 시도 비용을 같이 보고하도록 고친다(`docs/2026-10-28-claude-runner-design.md` 6절). 측정 세션을 쓰지 않는 원칙은 유지한다.
