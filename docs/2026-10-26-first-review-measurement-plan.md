# 첫 검토 검토자별 발견 능력 측정 계획 (2026-10-26)

같은 변경을 Claude(Fable·Opus)와 Codex가 각각 첫 검토했을 때 누가 무엇을 찾는지 잰다. 특히 Codex가 Claude 모델만으로는 못 잡는 「사실」 지적을 실제로 더 찾는지 본다. 2026-10-26 가성비 측정(`docs/2026-10-26-cost-effectiveness.md`)은 지적이 주어진 뒤의 수정 단계만 쟀다. 이 계획은 그 앞 단계(발견)를 잰다.

`docs/2026-10-21-role-profiles-measurement-plan.md` 4절 3단계 「첫 검토」의 코드 모드 부분을 따른다. 다른 점은 아래와 같다.

- 그 계획은 앞으로 할 실제 검토에서 모으는 방식(전향)이었다. 이 계획은 지난 PR의 **검토 전 상태**를 다시 검토하는 방식(소급)이다. 30건을 기다리지 않고 한 번에 모으기 위해서다.
- cascade-fix를 합친 목록으로 실제로 돌리지 않는다. 정답은 아래 4절 방식으로 정한다.

## 1. 검토 대상(1차 4개, 모두 cascade-fix 저장소)

squash로 합친 PR이라도 GitHub에 PR 커밋이 남아 있다(`refs/pull/<번호>/head`). 기능 커밋 뒤에 「바로잡는다」류 수정 커밋이 이어진 구간을 골라, **수정 커밋 직전 상태**를 검토한다. 다 고친 최종 상태를 검토하면, 개발 중 썼던 검토자(주로 Codex)가 이미 찾은 지적이 빠져 그 검토자에게 불리하기 때문이다.

| 대상 | PR | 검토 범위 | 변경 줄 | 뒤에 이어진 수정 커밋 |
| --- | --- | --- | ---: | --- |
| T1 | #15 사용량 기록 | `0378a6e^..aad6348` | +1,124 / −33 | `cf04740` |
| T2 | #15 score 표본 | `9107d7e^..9107d7e` | +352 / −41 | `3f98f4d` |
| T3 | #15 첫 검토 도구 | `5664bdf^..5664bdf` | +909 / −0 | `97525c9`, `5cbcdf4` |
| T4 | #15 회귀 집계 | `9e3d040^..9e3d040` | +486 / −0 | `e3cdc08` |
| T5 | #16 설정 마법사 | `459ad70^..0d47020` | +2,487 / −40 | `6c8e845`, `584508b`, `77861e8`, `1687196`, `2faf63b` |
| T6 | #18 Cursor ACP 읽기 범위 | `1fb42da^..1fb42da` | +306 / −43 | 없음 |
| T7 | #23 단일 Claude 기준선 | `275c52e^..97ea1de` | +1,882 / −21 | 없음 |

- 사용자 결정: 대상을 줄여서 시작한다. 1차는 T1·T3·T5·T6이다. 수정 커밋이 많은 구간(T5)과 보안 성격의 작은 변경(T6)을 함께 넣었다. 중복을 지운 지적이 30건이 안 되면 T4·T2·T7 순서로 더한다.
- 대상마다 PR 헤드를 가져와(`git fetch origin pull/<번호>/head`) 임시 워크트리를 범위 끝 커밋에 만들고, `--base <범위 시작의 부모>`로 검토한다. 검토가 끝나면 워크트리를 지운다.
- 지난 검토(2026-10-25 sample-be #782)에서 검토자 하나당 지적이 1~6건이었다. 대상 4개 × 검토자 3명이면 중복을 지운 뒤 30건 안팎으로 본다.
- 개인 계정 밖의 저장소는 넣지 않는다.

## 2. 검토자

| 검토자 | 명령 | 모델 |
| --- | --- | --- |
| Claude | `CF review --profile claude-only --root <워크트리> --kind code --base <base>` | Fable 5.1 high |
| Codex | `cd <워크트리> && RR --base <base>` | Codex 기본값 |
| Opus 단독 | `CF review --profile claude-only --review-model claude-opus-5-5 --review-effort high …` | Opus 5.5 high |

- 사용자 결정(2026-10-26): Cursor는 검토자로 쓰지 않는다. 좋은 Cursor 모델(Grok 4.7·GPT-5.6 Sol·Opus 5.5, 셋 다 시험 호출 성공)은 작업자 같은 세부 실행 칸에 쓰는 방안으로 따로 검토한다.

- 셋(넷) 모두 같은 워크트리·같은 base를 본다. 검토 초점(`focus`)은 주지 않는다. 2026-10-25 #782에서는 Claude에만 초점을 줘서 Codex(6건)와 Claude(1건)를 비교할 수 없었다.
- Opus 단독은 Fable과 같은 검토 지시문으로 모델만 바꾼다. 「Codex가 더 찾는가」와 「Claude 모델을 바꾸면 따라잡는가」를 나눠 보기 위해서다.
- 무거운 프로세스는 동시에 2개까지만 돌린다.

## 3. 합치기

- 대상마다 `python3 eval/first_review.py merge --claude <Fable 결과> --codex … --cursor <Opus 결과> --out <대상 폴더>`로 묶음 후보를 만든다(위치가 5줄 안이고 검토자가 다르면 같은 묶음 후보).
- 메인 세션이 묶음을 확정하고, 애매한 것은 사용자에게 보인다. 확정 뒤 `merge --confirm`.
- 지금 도구는 검토자 칸 3개(claude·codex·cursor)만 받는다. Cursor를 쓰지 않으므로 비는 cursor 칸에 Opus 결과를 넣고, 결과 문서에서는 이 칸을 「Opus」로 적는다. Opus 결과는 Claude와 같은 형식이라 cursor 칸의 파서(`parse_codex_doc`)로 읽힌다. 다만 비용은 Cursor 로그가 아니라 Opus의 `claude-usage.json`에서 따로 읽는다.

## 4. 정답 정하기

- 메인 세션이 묶음마다 코드를 읽고, 필요하면 테스트로 재현해 「사실·아님·재현 불가」 후보와 근거를 적는다.
- 판정할 때는 누가 찾았는지(`found_by`)를 가리고 본다. 판정하는 메인 세션도 Claude라 Claude 지적 쪽으로 기울 수 있기 때문이다.
- 같은 PR 뒤 수정 커밋이 고친 문제와 같으면 「사실」의 근거로 쓴다. 다만 결정 근거로만 쓰지는 않는다(개발 중 검토자의 시각이 섞여 있다).
- 판정 후보를 표로 사용자에게 보이고 확정받는다. 사용자가 고친 것은 결과 문서에 적는다.

## 5. 지표

`python3 eval/first_review.py score --merged <확정한 merged.json> --truth <정답.jsonl>`가 검토자별로 낸다.

- 정밀도 = 그 검토자 지적 중 「사실」 / 그 검토자 지적 수
- 재현율 = 그 검토자가 찾은 「사실」 / 전체 「사실」
- **그 검토자만 찾은 「사실」 수**(이번 측정의 핵심 질문). 등급별로도 나눈다.
- 비용: Claude는 `CF usage --review-dir`의 `claude-usage.json`, Cursor는 원본 로그 토큰, Codex는 토큰 기록이 없어 시간만 적는다.
