## 2. 비교할 구성

| 구성 | 첫 검토 | 비고 |
| --- | --- | --- |
| A (기준) | Fable 5.1 high | 지금 `claude-only` 값 |
| B | Opus 5.5 high | `--review-model claude-opus-5-5 --review-effort high`. Fable과 같은 지시문, 모델만 다름 |
| C | Codex 단독 | `cd <워크트리> && RR --base <base>`. Codex 기본값 |
| D | Fable + Codex 병행 | 합집합 |
| E | Opus + Codex 병행 | 합집합 |

- **D·E는 따로 돌리지 않는다.** 검토자는 서로 독립으로 돌아 서로 보지 않으므로, A·B·C 결과의 합집합이 병행 구성의 결과와 같다. 실행은 A·B·C 3종만 한다. 지난 측정의 「둘씩 짝지으면」 표와 같은 방식이다.
- Fable+Opus는 같은 회사의 모델 둘이라 지난 측정에서 Fable+Codex와 사실 수가 같았다(24/30). 이번에는 비교 후보로 올리지 않고 표에서만 보인다. 필요하면 A·B 합집합으로 계산할 수 있다.
- 시험하지 않는 것: Opus xhigh·Sonnet 첫 검토(미확인: 단가·효과), Cursor 검토자(2026-10-26 사용자 결정으로 제외).
- **병행 채택의 구현 문제(미확인 범위).** 프로필의 `<모드>.review`는 칸 하나뿐이라(`docs/reference.md`의 첫 검토 절), 한 실행에서 검토자 둘을 병행하는 경로가 지금 있는지 확인하지 못했다. `default` 프로필의 `auto`는 둘 중 하나를 고르는 것이지 병행이 아니다(`docs/reference.md` 175줄). 그리고 `claude-only`는 Codex가 없는 환경용 기준 프로필이다. D·E가 이기더라도 「`claude-only` 값을 바꾼다」가 아니라 「새 프로필 또는 병행 기능을 만든다」가 되므로, 측정 뒤 별도 설계 결정이 필요하다.

## 3. 표본 확대 방안

### 3.1 반복(검토자 흔들림 재기)

- 지난 대상 중 **T1·T4·T5** 3개를 A·B·C로 각각 2회 더 돌린다(총 3회). 정답은 이미 있으니, 새로 나온 묶음만 판정한다.
- 얻는 것: 같은 검토자가 같은 대상에서 찾는 사실 수의 최소~최대 범위(참고로 사실 집합의 겹침). 이 범위가 「A와 B의 차이가 흔들림보다 큰가」를 판단하는 기준 폭이다. 반복 회차는 합계 채점에 넣지 않는다(6절).
- 선정 이유: T5는 가장 커서(+2,473줄) 지적이 많고, T4는 작아서 싸고, T1은 중간이다. T6은 Cursor 경로 의존 판정이 많아(재현 불가 2개) 뺐다. T3은 측정 도구 자신이라 뺐다. 이 선정은 사용자가 바꿀 수 있다.

## 4. 검토자 실행

지난 측정과 같은 명령·같은 방식으로 돌린다.

| 검토자 | 명령 | 모델 |
| --- | --- | --- |
| A | `CF review --profile claude-only --root <워크트리> --kind code --base <base>` | Fable 5.1 high |
| B | 위에 `--review-model claude-opus-5-5 --review-effort high` | Opus 5.5 high |
| C | `cd <워크트리> && RR --base <base>` | Codex 기본값 |

- 셋 모두 같은 워크트리·같은 base. 검토 초점은 주지 않는다.
- 대상마다 PR 헤드를 가져와(`git fetch origin pull/<번호>/head`) 임시 워크트리를 범위 끝 커밋에 만들고, 끝나면 지운다. 워크트리 안에서 `python3 -m cascade.cli review`를 돌리지 않는다(지난 「옛 코드로 만든 검토 작업」 재발 방지. `--root`만 대상으로 준다).
- 외부 저장소의 Claude 검토는 Workflow로 돌리고 `CF usage --review-dir`로 토큰을 기록한다. Codex는 한 번에 하나씩 차례로 돌린다.
- 반복 실행은 **새 결과 폴더**에 둔다(같은 폴더를 덮지 않는다). 각 반복은 `merge`의 세 칸(claude·codex·cursor 칸에 A·C·B)을 꽉 채우므로, 반복 회차는 `T1-run2`처럼 회차별 폴더에 따로 합친다. 합계 채점에는 대상당 1회차만 넣는다(6절).
- 무거운 프로세스는 동시에 2개까지. 예상 메모리는 검토 한 건당 Claude 쪽 Workflow 하나(미측정, 지난 측정에서 이상 보고 없음), Codex CLI 하나다. 시간 제한은 둘로 나눠 정한다.
  - **Codex**: `perl -e 'alarm shift; exec @ARGV'`는 부모 셸만 죽인다. `run-review.sh`가 `codex review`를 자식으로 띄우고 정리 코드(`trap`)에는 자식을 죽이는 것이 없어(`docs/codex-review-changes/run-review.sh` 172~186줄 부근), 자식 Codex가 남아 「Codex는 한 번에 하나」가 깨질 수 있다. 그래서 **실행마다 새 프로세스 그룹**을 만들어 그룹 전체에 제한을 건다(이 기기에서 `bash -c 'sleep 300 & wait'`로 시험해 exit 142, 자식도 종료됨을 확인했다). 이 절차를 쓴다.
    ```bash
    perl -e 'my $t = shift; my $pid = fork; if (!$pid) { setpgrp(0, 0); exec @ARGV or die } $SIG{ALRM} = sub { kill "TERM", -$pid; sleep 5; kill "KILL", -$pid; waitpid($pid, 0); exit 142 }; alarm $t; waitpid($pid, 0); my $s = $?; exit($s & 127 ? 128 + ($s & 127) : $s >> 8)' 1800 bash -c 'cd <워크트리> && RR --base <base>'
    ```
    종료 코드는 정상 0, 오류는 그 코드, 자식이 시그널로 죽으면 128+시그널 번호(예: TERM 143), 시간 초과 142다. 실행 전에 `bash -c 'exit 0'`·`'exit 7'`·`'kill -TERM $$'`·`'sleep 300 & wait'`를 넣어 각각 0·7·143·142가 나오고 자식이 안 남는지 확인한다(이 기기에서 확인함). 래퍼가 시그널 종료를 0으로 돌리면 중단된 실행이 정상 완료로 보이므로 `exit($? >> 8)`만 쓰는 형태는 쓰지 않는다.
    초과(142) 또는 0이 아닌 종료 뒤에는 `ps -axo pid,pgid,command | grep -i '[c]odex'`로 이 실행의 Codex 프로세스가 남지 않았음을 확인하고, 남았으면 `kill -KILL`로 정리한 뒤에만 다음 실행·재시도를 한다. 재시도는 한 번까지고 그 실행은 결과 없음으로 기록한다.
  - **Claude(Fable·Opus) Workflow**: `CF review`는 Workflow 입력(`review-args.json`)만 만들고(`cascade/cli.py`의 `_emit_first_review`), `scripts/run-jobs.js`는 에이전트 호출에 시간 제한이 없다(`pipeline(jobs, … agent(…))`만 있음). 그래서 셸 시간 제한으로는 못 막는다. 메인 세션이 Workflow 시작 시각을 `runs.md`에 적고, **지난 평균의 약 3배(Fable 20분, Opus 12분)를 넘으면 `TaskStop`으로 그 Workflow를 멈춘다.** 멈춘 뒤 Workflow 목록에 실행 중으로 남아 있지 않은지 확인하고 나서야 같은 지시문으로 다시 돌린다(이전 Workflow가 `review.json`을 덮어쓸 수 있어 확인 전에는 재시도하지 않는다). 재시도는 대상·검토자당 1회까지고, 또 초과하면 그 칸을 결측으로 두고 보고한다. 지난 T6 Fable처럼 네트워크 끊김(1시간 55분)이 평균 시간을 왜곡하므로 시간 통계에서는 재시도·중단 실행을 뺀다.
- 결과 폴더는 `~/01.workspace/backup/cascade-fix-eval-runs/2026-10-28-first-review-config/`(git 밖, 커밋하지 않음).

## 5. 합치기·정답 정하기

- **하나로 합쳐 채점할 때는 묶음 id뿐 아니라 지적 id와 묶음 멤버의 지적 참조에도 대상 이름을 붙인다**(지난 `merged-all.json`처럼 `T1-r1-01`, `T1-g01`). `merge`가 만드는 지적 id는 대상마다 `r1-01`부터 다시 시작해(`eval/first_review.py`가 파서에 회차 1을 넘김), 묶음 id만 바꾸면 `(runner, id)` 키가 대상 사이에 겹쳐 `check_groups`가 「중복 배정」으로 채점 전체를 거절한다(`eval/first_review.py:196·224`). 합치는 일은 도구에 없어 스크립트로 하고, 합친 뒤 `score`가 오류 없이 도는지 확인한다.
- `python3 eval/first_review.py merge …`로 묶음 후보를 만든다. 위치 5줄 안·다른 검토자면 같은 묶음 후보이고, 메인 세션이 본문을 대조해 확정한다(지난 방식).
- **Codex 절대 경로 문제.** 지난 측정에서 `merge`가 Codex의 절대 경로 위치를 상대 경로로 맞추지 못해 경로를 지운 사본(`review.rel.txt`)을 따로 만들었다. 이 도구 수정이 이미 들어갔는지 확인하지 못했다(미확인; 이 워크트리 `eval/first_review.py`에서 상대 경로 처리 코드를 찾지 못했다). 36 실행 중 12개가 Codex이므로, 수정이 없으면 같은 수작업을 12번 한다. 실행 전에 확인하고 필요하면 먼저 고친다(별도 작업).
- 정답 판정은 지난 방식을 따른다. 검토자 이름을 가린 묶음 목록을 하위 에이전트가 받아 코드를 읽거나 재현해 「사실·아님·재현 불가」 후보와 근거를 낸다. 사용자가 후보를 표로 확인한다.
- **반복 회차의 묶음은 지난 정답과 대조한다.** 같은 대상·같은 문제로 보이는 묶음은 지난 판정을 그대로 쓰고, 새 묶음만 판정한다. 같은 문제인지 정하는 기준은 지난 `merge`의 묶음 기준(위치 5줄·본문 대조)과 같게 한다. 도구가 반복 간 묶음을 잇지 못하므로 메인 세션이 수작업으로 한다(미확인: 새 묶음이 몇 개나 나올지).
- **판정자 편향 점검.** 지난 판정자는 Opus 하위 에이전트였고, 이번 비교에 Opus가 검토자로 들어 있다. 같은 모델이 자기 계열 지적을 후하게 볼 수 있다. 대응: ① 판정 때 검토자 이름을 가린다(지난과 같음). ② 판정 근거의 대부분을 재현 스크립트로 둔다(지난 28/38). ③ 판정자 모델을 바꿀지는 사용자가 정한다(10절). 바꾸면 비용이 늘어난다.
- 정답이 비어 사실 수 분모가 흔들리는 것을 막기 위해, **정답은 검토 결과를 모두 합쳐 한 번에 확정한 뒤** 채점한다. 검토자를 하나씩 채점하며 정답을 늘리지 않는다.

## 6. 지표

`python3 eval/first_review.py score --merged <확정한 merged.json> --truth <정답.jsonl>`가 검토자별로 낸다. 저장소·대상별 표를 나눠 보고, 합계는 대상 이름을 묶음 id 앞에 붙여 하나로 합쳐 채점한다(지난 방식).

| 지표 | 정의 | 비고 |
| --- | --- | --- |
| 정밀도 | 그 검토자 지적 중 「사실」 / 지적 수 | 윌슨 95% 구간을 함께 적는다 |
| 잃는 사실(Fable→Opus) | Fable이 찾은 「사실」 중 Opus가 못 찾은 수(`Fable 사실 − Opus 사실`). Warning 이상 수도 따로. **등급은 묶음 등급이 아니라 그 묶음에서 Fable 자신이 붙인 등급**을 쓴다 | 7.1의 3번 기준. 「단독 사실」은 둘 다 못 찾은 것만 세므로 이 값이 아니다 |

- **추가 계산.** 윌슨 구간·잃는 사실·병행 구성 비용·흔들림(`D`·`W`)은 `score`가 내지 않는다. 실행 전에 확정한 `merged-all.json`과 정답 jsonl을 읽어 이 값들을 내는 일회용 스크립트를 결과 폴더에 둔다(저장소 코드는 바꾸지 않음). 검증: 지난 `merged-all.json`·`truth.jsonl`로 돌려 지난 문서의 값(Fable 14/20, Opus 13/13, 조합 Fable+Opus 24/30 등)이 그대로 나오는지 확인한 뒤 새 데이터에 쓴다. 병행 구성의 「지적 수」는 원본 지적 수가 아니라 **중복을 제거한 묶음 수**로 센다(`confirm`이 묶음마다 수정 입력 하나를 만든다). 같은 지적을 두 검토자가 찾은 묶음(지난 T1-g01)이 한 번만 세어지는지 확인한다.
- 수정 단계 비용은 회차 3개 평균이고 날짜가 다른 측정값이라 이번 시점 단가와 다를 수 있다(미확인). 비용은 보조 지표이고 판정의 중심이 아니다.
- **반복에서 새로 나온 사실의 처리.** `score`는 정답 파일에 묶음 id가 모두 있어야 하고 입력 밖 id가 있으면 거절하며(`check_truth`), 모든 지적이 어느 묶음에든 배정돼야 한다(`check_groups`). 그래서 채점은 **회차마다 자기 `merged.json`과 자기 정답 파일**로 한다. 1회차 정답은 지난 방식대로 정하고, 2·3회차는 같은 문제로 보이는 묶음은 대상별 고정 정답을 그대로 가져오고(5절), 새 묶음만 판정해 그 회차 정답 파일에 더한다. **대표 채점(1회차 합계)의 재현율 분모는 1회차 묶음의 사실만이며, 2·3회차에서만 나온 사실은 넣지 않는다.** 이 때문에 재현율은 관측된 사실 기준의 값이다. 관측되지 않은 사실이 분모에 없어 실제 재현율보다 높게 나올 수 있고(반복에서 사실이 하나 더 확인되면 같은 실행의 재현율이 내려간다), 세 검토자에 같은 분모라 검토자 사이 비교만 유지된다. 2·3회차에서 새로 나온 사실은 「회차 추가 사실」로 따로 세어 보고한다(검토자별 수). 흔들림(위)은 분모 없이 회차별로 찾은 사실 수만 쓰므로 이 구분의 영향을 받지 않는다.
- **검토 실행의 완료 조건.** 병합 성공만으로는 「지적 없음」과 「실패·파싱 누락」을 구분하지 못한다(`parse_codex_code`는 오류 문장만 있는 입력도 빈 목록으로 반환하고, `merge`는 해석하지 못한 항목을 경고만 하고 끝낸다). 한 실행을 **완료**로 인정하는 조건은 ① 원본 실행이 종료 코드 0으로 끝남(Codex는 위 래퍼, Claude는 Workflow가 성공으로 끝나고 `review.json`에 결과가 있음), ② 결과 파일(`review.out.final`·`review.json`)이 존재하고 비어 있지 않음, ③ `unparsed_code_items`로 읽지 못한 항목이 0건(지난 측정에서도 한 확인), ④ 지적이 0건이면 원문을 읽어 정상적인 「지적 없음」 문장인지 확인함이다. 하나라도 어긋나면 그 실행은 **결측**으로 처리한다.
- **결측 실행(재시도도 실패한 칸) 처리.** `score`는 합친 입력에 검토자 결과가 없으면 그 검토자를 계산에서 빼므로(`given`, `eval/first_review.py:359`), 미실행과 미발견이 섞이지 않게 규칙을 둔다. ① 대표 비교(7.1·7.2 판정, 합계 표)에는 **1회차 A·B·C가 모두 완료된 대상만** 넣는다. 한 검토자라도 결측이면 그 대상은 대표 비교에서 빼고 결측 목록(대상·검토자·사유)에 적는다. ② 결측 대상에서 나온 지적은 정답 판정·비용에도 쓰지 않는다(판정 비용 절약). ③ 흔들림은 검토자·대상별로 **완료한 회차가 2개 이상일 때만** 계산하고, 미만이면 그 대상은 7.1의 5번(`D`·`W`)에서 뺀다. 빠진 뒤 대상이 1개 이하면 7.1의 5번은 판정 불가로 7.4를 따른다. ④ 결측이 한 검토자에 몰렸거나 새 저장소 대상이 절반 이상 빠지면 결과를 확정하지 않고 사용자에게 보고한다(결측이 모델·저장소 특성과 관련됐을 수 있다).
- **합계 채점은 대상당 1회차만 넣는다.** 반복 회차를 별도 대상으로 합산하면 같은 사실이 회차마다 별개 묶음으로 잡혀 재현율 분모가 부풀고 반복 대상이 가중된다(`eval/first_review.py`의 `reviewer_score`는 모든 묶음을 같은 가중으로 센다). 반복 회차(2·3회차)는 회차별로 따로 채점해 흔들림(위)과 회차 평균을 보는 데만 쓴다. 정밀도·재현율의 대표값은 1회차 합계다.
- **Opus 결과를 cursor 칸에 넣는 절차.** `merge --cursor`는 파일을 그대로 읽으므로(`read_result_text`는 claude 칸만 `review.json`을 풀어 읽는다) Opus의 `review.json`을 직접 줄 수 없다. `review.json`의 `results`에서 `id`가 `review:reviewer`인 항목의 `output.text`를 `review.txt`로 꺼내(지난 `opus/<대상>/review.txt`와 같은 방식) 그 파일을 준다. 꺼낸 뒤 ① `output.model_id`가 요청한 모델(`claude-opus-5-5`)과 같은지, ② `review.txt`의 번호 항목 수가 `merge` 출력의 cursor 칸 지적 수와 같은지 대조한다. 어긋나면 완료 조건 ③ 위반으로 그 실행을 결측으로 둔다.
- **비용 칸.** Opus 결과는 cursor 칸에 넣으므로 `score` 출력의 「Cursor」 행이 Opus의 정밀도·재현율·단독 사실이다(그 행의 비용은 Cursor 로그 기준이라 쓰지 않는다). Opus 비용은 `--usage-claude <Opus의 claude-usage.json>`을 주어 **같은 `score`를 다시 돌려, 그 출력의 「Claude」 행 비용**에서 읽는다(그 실행의 Claude 행 지표는 Fable의 것이라 비용만 쓴다). Fable 비용은 `--usage-claude <Fable의 claude-usage.json>`으로 돌린 Claude 행에서 읽는다. 한 번에 둘의 비용을 낼 수 없다. 결과 문서에는 「Cursor」 행을 「Opus」로 적는다.

## 7. 판정 기준

실행 전에 정해 둔다(결과를 보고 기준을 옮기지 않는다). 표본이 작아 **방향 판정**이다. 기준은 9절의 한계를 감안한 값이고, 사용자가 바꿀 수 있다.

### 7.1 Fable → Opus로 바꾼다

다음을 모두 만족하면 `claude-only` 첫 검토를 Opus로 바꾸는 안을 올린다.

1. 전체(지난 5개 + 이번 대상 합계)에서 Opus 재현율이 Fable보다 5%포인트 넘게 낮지 않다.
2. Opus 정밀도가 Fable 이상이다.
3. **Fable이 찾았지만 Opus가 못 찾은 사실 중 Warning 이상이 전체 사실의 5% 이하**다(6절 「잃는 사실」). 즉 바꿀 때 잃는 것이 대부분 Suggestion급이어야 한다. 지난 측정에서 Fable 단독(Opus·Codex 모두 못 찾음) Warning은 1개(T4-g01)였지만 Opus만 못 찾은 Fable 사실 수는 지난 문서에 없다(미확인, 실행 전 `merged-all.json`에서 계산한다).
4. 새 저장소 3개 중 2개 이상에서 저장소별로 1·2번과 같은 부등호가 성립한다(Opus 재현율 ≥ Fable − 5%포인트, Opus 정밀도 ≥ Fable). 3번은 저장소별 사실이 너무 적어 합계로만 본다. 지난 결과가 cascade-fix에 치우친 것이 아님을 본다.
5. 반복 3개 대상의 흔들림으로 모델 차이를 가른다. 검토자 X·대상 t의 회차별 찾은 사실 수에서 평균 m(X,t)와 **폭 w(X,t) = 최대 − 최소**를 구한다. `D = 3개 대상 평균 [m(Fable,t) − m(Opus,t)]`(평균 차이), `W = 3개 대상 평균 [max(w(Fable,t), w(Opus,t))]`(두 검토자 폭을 합치지 않고 큰 쪽을 쓴다). `D ≤ W`면 Fable이 더 찾는다고 말할 수 없는 흔들림 안이라 1~4번만 본다. `D > W`면 Fable이 실제로 더 찾는 것이므로 1번을 「Opus 재현율이 Fable 이상」(허용 0%포인트), 3번을 「잃는 Warning 이상이 전체 사실의 3% 이하」로 조여서 다시 판정한다. `D < 0`(Opus가 더 찾음)이면 추가 조건이 없다. 회차가 3개뿐이라 폭 자체가 거친 추정이다. **`D`·`W`를 계산할 수 없으면**(결측 처리 후 반복 대상이 1개 이하, 5절) 「흔들림 안」으로 보지 않는다. 이때는 `D > W`일 때와 같이 조인 값(재현율 허용 0%포인트, 잃는 Warning 이상 3% 이하)으로 1~4번을 판정하고, 통과해도 사용자에게 「흔들림을 재지 못했다」고 함께 올린다. 추가 반복을 돌릴지는 사용자가 정한다(자동으로 돌리지 않는다). 임계값(5%포인트·5%·3%)은 사용자가 승인한 뒤 실행 전에 고정한다(10절).

대상당 Claude 비용은 Fable $3.20 → Opus $1.24(추정)로 약 60% 줄어든다. 조건을 못 채우면 Fable을 유지한다. 조건을 통과한 뒤 차이가 흔들림 안이면 비용이 낮은 쪽(Opus)을 택한다(7.4의 순서).

### 7.2 Codex를 함께 돌린다(D 또는 E)

다음을 모두 만족하면 병행 안을 올린다. 올린다는 것은 설계·구현을 시작한다는 뜻이다(2절 끝).

1. **Codex 단독 사실이 새 저장소 대상 합계(1회차)에서 그 합계 사실의 10% 이상**이고, 새 저장소 3개 중 2개 이상에서 각각 1개 이상 나온다. 지난 20%(6/30)가 cascade-fix만의 결과인지를 가른다.
2. 그중 Warning 이상(동작 결함) 단독 사실이 3개 이상이다.
3. Codex 정밀도가 80% 이상이다(지난 87%).
4. 병행 안의 이득이 비용을 넘는다. 비교 기준은 Codex를 뺀 같은 Claude 구성이다(D는 A, E는 B). 병행의 「사실 1개당 총비용」(6절, 지적 수는 중복 제거한 묶음 수)이 그 구성의 1.5배 이하이고, 병행으로 늘어나는 사실 아닌 묶음 수가 늘어나는 사실 수보다 적다. 같은 계산을 D와 E 모두에 하고, 통과한 쪽만 후보다.

병행이 필요하지 않다고 보는 경우: Codex 단독 사실이 새 저장소에서 거의 나오지 않으면 Codex 이득은 cascade-fix 코드(Claude가 쓴 Python)에 한정된 것으로 본다.

### 7.3 D와 E 중 고르기

7.2를 통과하면 7.1이 Opus 전환을 올렸으면 Opus+Codex(E), 올리지 않았으면 Fable+Codex(D)를 후보로 한다. 7.2의 4번을 D·E 중 한쪽만 통과하면 그쪽만 후보다. 둘 다 못 통과하면 병행은 올리지 않는다. 7.1과 7.2는 독립이라 둘 다 통과·둘 다 실패·한쪽만 통과가 모두 가능하다. 지난 측정에서 Opus+Codex는 정밀도·비용이 좋았고 재현율이 70%였다.

### 7.4 판정 불가

- **결정 순서(우선순위).** ① 품질 조건(7.1의 1~4번, 흔들림 초과 시 조인 값)을 먼저 적용한다. 통과하지 못한 후보는 비용이 낮아도 올리지 않고 Fable을 유지한다. ② 품질 조건을 통과한 뒤에만, 7.1의 5번에서 차이가 흔들림 안(`D ≤ W`)이면 「차이 없음」으로 적고 비용이 낮은 쪽(Opus)을 기본으로 사용자에게 올린다. 7.1 끝의 「Opus가 Fable과 같으면 Opus」는 이 ② 경우만을 뜻한다.
- 새 저장소의 사실이 너무 적으면(합계 25개 미만) 7.2의 비율·저장소 기준(1번)을 쓰지 않는다. 이때 병행 안은 올리지 않고(보류) 개수만 보고하며, 추가 표본을 돌릴지는 사용자가 정한다. 7.1의 판정은 합계(지난 포함) 기준이라 영향이 없다.

## 9. 위험·한계

- **표본이 여전히 작다.** 사실 70~75개로도 재현율 몇 %포인트 차이는 구분할 수 없다. 7절 기준을 방향 판정으로 둔 이유다. 결과가 기준 근처에 걸리면 추가 표본이 필요하다고 보고한다.
- **소급 측정이고 대상이 Claude가 쓴 코드일 수 있다.** 새 저장소의 코드 작성 주체는 미확인이다. Claude가 쓴 코드면 Claude 검토자와 맹점을 공유하고, 사람이 쓴 코드면 Codex 이득이 달라질 수 있다. 저장소별 작성 주체(Claude/사람/혼합)를 선정 때 적어 보고한다.
- **수정 커밋 근거 약화.** cascade-fix는 PR 안 수정 커밋으로 사실을 보강했지만, 다른 저장소는 수정 커밋이 없는 구간도 있다. 재현 스크립트 비중이 늘어 판정 비용이 오른다.
- **판정 편향.** 판정자가 Claude 계열이고(5절), 정밀도 100%(13/13) 같은 값은 판정이 후했을 가능성도 있다. 사용자 확인이 마지막 방어선이다.
- **실행 조건 기록.** 지난 측정은 Codex를 「기본값」이라고만 적었다. `run-review.sh`는 `~/.codex/config.toml`의 `model`·`model_reasoning_effort`를 임시 홈으로 옮기므로(`docs/codex-review-changes/run-review.sh` 96~100줄 부근) 「기본값」은 그 기기 설정에 달렸다. 지난 `codex/T1/review.out` 헤더에는 `model: gpt-6.1-sol`, `reasoning effort: high`가 있다. 실행 시작 전과 **매 실행마다** `runs.md`에 적는다.
  - Fable·Opus: `review-meta.json`의 요청 모델·effort, `review.json`의 `model_id`(실제 쓴 모델), 검토 지시문(`prompts/review-reviewer.md`에서 만든 프롬프트)의 해시.
  - Codex: `codex --version`(이 기기 지금 `codex-cli 0.163.0-alpha.10.2`), 실행 파일 경로, `review.out` 헤더의 model·reasoning effort, `~/.codex/config.toml`의 model·effort, `run-review.sh`의 경로와 sha256.
  - 공통: cascade-fix 커밋(검토 도구·`eval/first_review.py`).
  - 지난 측정에서 기록이 없는 것(Codex CLI 버전, `run-review.sh` 해시)은 「미확인」이다.
  - **대조 규칙.** 모델 id·reasoning effort가 지난 값과 같으면 같은 조건으로 보고 합산한다. CLI 버전·스크립트 해시 차이는 기록하고 결과 문서에 적되 합산을 막지는 않는다(지난 값이 미확인이라 비교할 수 없다). 모델 id 또는 effort가 다르면 지난 결과는 합계에서 빼고(참고용) T1·T4·T5는 새 회차로, T3·T6은 재실행 여부를 사용자가 정한다. 실행 도중 조건이 바뀌면(예: 모델 id가 중간에 달라짐) 멈추고 보고한다. 조건이 다른 실행은 한 합계에 섞지 않는다.
- **모델·Codex 버전 변화.** 지난 측정(2026-10-26)과 이번 사이에 Fable·Opus·Codex 기본 모델이 바뀌면 지난 5개 대상 값과 새 값을 합칠 수 없다. 실행 시작 때 세 검토자 모델 id를 적어 두고, 달라졌으면 지난 값을 합계에서 빼고 새로 잰다(그러면 지난 5개 대상도 다시 돌려야 해 비용이 는다, 미확인). 반복 3개 대상이 이 점검 겸용이다: 지난 결과와 사실 집합이 크게 다르면 모델 변화나 흔들림이다.
- **Codex 한도.** 36 실행 중 Codex 12회가 ChatGPT 구독 한도를 얼마나 쓰는지 알 수 없다(토큰 기록 없음). 한도에 걸리면 중간에서 멈추고 보고한다.
- **외부 전송.** 11절 표의 동의를 실행 전에 받는다.
- **도구 공백.** Codex 절대 경로 병합, 반복 회차 간 같은 지적 잇기, 3칸(claude·codex·cursor)에 Opus를 넣는 우회(결과 문서에서 「Opus」로 적음)는 지난과 같다. 이번에는 이 우회가 반복 12회에 걸쳐 되풀이되므로 실수 위험이 크다. 칸 이름을 바꾸는 도구 변경은 별도 작업이고, 이번 계획에는 넣지 않았다.
- 이 계획은 첫 검토만 본다. 지적이 늘면 수정 단계 비용이 는다(6절 「사실 1개당 총비용」으로 환산할 뿐 새로 재지 않는다).
