# 첫 검토 검토자별 발견 능력 측정 (2026-10-26)

같은 코드 변경을 Claude(Fable 5.1·Opus 5.5)와 Codex가 각각 첫 검토했을 때 누가 무엇을 찾는지 쟀다. 계획은 `docs/2026-10-26-first-review-measurement-plan.md`에 있다. 2026-10-26 가성비 측정(`docs/2026-10-26-cost-effectiveness.md`)은 지적이 주어진 뒤의 수정 단계만 쟀고, 이 측정은 그 앞 단계(발견)를 잰다.

**결과: Codex는 Fable과 Opus가 둘 다 놓친 「사실」 지적을 6개 찾았다(전체 사실 30개 중 20%). 6개 모두 동작 결함이었다(크래시, 설정 파일을 조용히 잘못 고침, 시험이 거짓으로 통과함 등). 세 검토자는 서로 겹치는 것이 거의 없었다. 셋이 함께 찾은 사실은 1개뿐이고, 검토자 하나의 재현율은 43~47%, 둘을 합치면 70~80%다. 정밀도는 Opus 100%(13/13), Codex 87%(13/15), Fable 70%(14/20)다. Fable이 혼자 찾은 사실 9개 중 8개는 Suggestion 등급(메시지·주석·문서·드문 입력)이었다. 첫 검토 Claude 비용은 대상당 Fable $3.20, Opus $1.24다. Codex는 ChatGPT 구독 한도로 돌아 Claude 비용이 들지 않는다.**

## 잰 방법

1. 대상마다 Fable·Opus 검토를 `CF review`로 만들어 Workflow로 돌리고, `CF usage --review-dir`로 토큰을 기록했다. Codex는 한 번에 하나씩 차례로 돌렸다.
2. `eval/first_review.py merge`로 세 결과를 합쳤다. Opus 결과는 도구의 세 번째 칸(cursor)에 넣었다. 그래서 `score` 출력의 「Cursor」 줄이 Opus다.
3. 묶음 후보(위치 5줄 안, 다른 검토자)를 본문과 대조해 확정했다. 위치가 멀어도 같은 문제면 합쳤고(T5 2쌍), 위치가 같아도 다른 문제면 나눴다(T6 2쌍). 합친 지적 48건(Fable 20, Codex 15, Opus 13) → 묶음 38개.
4. 정답: 대상마다 하위 에이전트(Opus)가 검토자 이름을 가린 묶음 목록을 받았다. 각 묶음을 그 시점 코드에서 읽거나 재현해 「사실·아님·재현 불가」 후보와 근거를 냈다. 38개 중 28개를 재현 스크립트로, 10개를 코드 읽기로 확인했다. PR의 나중 수정 커밋이 같은 문제를 고쳤으면 「사실」 쪽 근거로만 썼다. 사용자가 후보 38개를 그대로 확정했다(2026-10-27).
5. `eval/first_review.py score`로 검토자별 정밀도·재현율·단독 사실(이번에 더한 열, 아래 「도구 변경」)·비용을 냈다. 대상 다섯은 묶음 id 앞에 대상 이름을 붙여 하나로 합쳐 채점했다.

판정 기준:

- **사실**: 지적한 결함이 그 시점 코드에 실제로 있다. Suggestion 등급이라도 결함이 있으면 사실이다.
- **아님**: 주장이 틀렸거나(그렇게 동작하지 않음, 전제가 생길 수 없음) 결함이 아니다(의도된 설계, 취향).
- **재현 불가**: 코드만으로 확인할 수 없고 재현도 못 했다.

## 측정 중 생긴 일

- **네트워크 끊김.** 처음 띄운 Fable 검토 4개 중 3개가 약 1시간 45분 동안 API 서버에 닿지 못하고(ENOTFOUND) 결과 없이 끝났다. 네트워크가 돌아온 뒤 같은 지시문으로 다시 돌렸다. T6은 끊긴 채 기다리다 이어서 끝나 결과를 그대로 썼다(시간만 평균에서 뺐다).
- **옛 코드로 만든 검토 작업.** 처음에 대상 워크트리 안에서 `python3 -m cascade.cli review`를 돌려, 그 워크트리의 옛 cascade 코드가 검토 작업을 만들었다. 검토를 돌리기 전에 알아채 지우고, 이 워크트리 코드로 다시 만들었다(`--root`만 대상으로 줌).
- **Codex 위치가 절대 경로.** Codex 결과의 위치가 `/private/tmp/…/T1/cascade/report.py:610`처럼 워크트리 절대 경로였다. 상대 경로인 Claude 지적과 같은 묶음 후보로 잡히지 않아, 워크트리 경로를 지운 사본(`codex/<대상>/review.rel.txt`)으로 합쳤다. `first_review.py merge`가 경로를 맞추지 않는 문제다(「다음」).
- **Codex 결과 본문이 두 번 들어 있음.** `review.out.final`에 같은 요약·지적이 두 번 적혀 있었다. 파서가 같은 지적을 하나로 읽어 지적 수에는 영향이 없다.
- **나중 수정 커밋 목록 누락.** 대상을 고를 때 `gh pr view --json commits`의 앞 20개만 봤다. ## 한계

- **표본이 작다.** 사실 30개, 대상 5개, 검토자마다 1회다. 검토자 출력은 실행마다 흔들리므로 한두 개 차이는 의미가 없다. 「겹침이 적다」와 「Codex 단독 6개가 모두 동작 결함」은 방향으로 보고, 비율은 확정값으로 보지 않는다.
- **대상이 한 저장소다.** 모두 Claude가 쓴 cascade-fix Python 코드다. 다른 언어·저장소로 일반화하지 않는다.
- **소급 측정이다.** 개발 중 검토(주로 Codex·Claude)가 이미 본 코드다. 모델이 이 저장소를 기억하지 않는다고 가정했다.
- **판정자도 Claude다.** 검토자 이름은 가렸지만 Codex 지적은 영어라 알아볼 수 있었다. 판정은 대부분 재현으로 정했고(28/38) 사용자가 확정했다.
- **같은 문제의 기준.** 묶음은 내가 본문을 대조해 정했다. 같은 함수의 다른 결함은 나눴는데, 이 경계에 따라 단독 수가 1~2개 바뀔 수 있다(T6 g01·g05, g02·g06).
- **경계 사례.** T5-g03(주석 위치)과 T4-g07(구간 밖 집계)은 사실로 확정했지만 판단이 갈릴 수 있다. 둘 다 아님으로 보면 Fable 단독 8개, Opus 단독 5개가 된다.

## 해석

- **Codex는 Claude만으로는 못 찾는 동작 결함을 찾는다.** Fable과 Opus를 둘 다 돌려도 놓친 사실 6개를 Codex가 찾았고, 모두 크래시·잘못된 결과·거짓 통과였다. 사용자가 말한 「Claude가 놓치는 지적을 찾아 품질을 높인다」는 목적에 맞는 결과다.
- **반대도 성립한다.** Codex가 놓친 사실 17개를 Claude 쪽이 찾았다. Codex만 쓰면 사실의 57%를 놓친다.
- **둘을 고르면 Opus + Codex가 가성비가 가장 좋다.** 정밀도가 가장 높고(사실 아닌 지적 2개), Claude 비용은 Fable + Opus의 28%다. 재현율은 70%로, Fable이 낀 조합(80%)보다 사실 3개를 덜 찾는다. 덜 찾는 것은 주로 Fable이 혼자 찾는 Suggestion급(메시지·주석·문서)이다.
- **Fable은 많이 찾고 많이 틀린다.** 지적 수와 재현율이 가장 높지만 「아님」·「재현 불가」 6개가 모두 Fable에서 나왔다. 비용도 Opus의 2.6배다.
- 이 측정은 첫 검토만 본다. 지적이 많아지면 그만큼 수정 단계 비용(진행 비용 지적당 약 $0.80, 가성비 측정)이 는다. 사실 아닌 지적은 수정 단계에서 걸러지지만 비용은 든다.
